# Authentication investigation: Telegram iPhone WebView

**Target:** `https://web-cdry.vercel.app`
**Repository revision inspected:** `24883af14d5fced39f8d6978caeb1ae84733e4b0`
**Scope:** Trace Google and Telegram sign-in, investigate the shared reported message, make scoped UI/test improvements, and verify what could be observed from this workspace.

## Finding

The displayed message is not generated by either provider's authentication callback. In `apps/web/features/live/AuthForms.tsx`, both tabs use one `GET /auth/providers` request. Any rejection of that request—network exception, non-2xx response, or an unsuccessful/unparseable response envelope—sets `providerLoadError`; the render branch then incorrectly names whichever provider tab Deborah selected (“could not reach Google/Telegram sign-in”). It therefore masks a **shared Deborah API/provider-discovery failure** as a provider-specific failure. This branch occurs before a Google credential or Telegram login payload is submitted.

That is the proven immediate cause of the displayed wording. **The originating event for Deborah’s particular iPhone attempt is not proven**: the repository contains no client telemetry for that request, and no iPhone Telegram WebView or server logs were available. At the time of inspection, the production `GET https://web-cdry.vercel.app/api/auth/providers` returned **HTTP 200 in about 0.3 seconds** with both public provider settings present. Thus the shared discovery endpoint was healthy during the probe; this does not establish its status on Deborah’s device at the failure time. No redirect loop was observed or is involved in the message-producing branch.

The API helper distinguishes fetch-level network failure as `ApiError(status=0, code=NETWORK)`. HTTP errors and invalid/unsuccessful JSON envelopes also reject, but become a separate `ApiError` with the returned HTTP status. The old `providerLoadError` catch discarded that distinction and rendered the same text for every case. Client/runtime and Vercel/Render request logs for the historical mobile attempt were unavailable, so a network exception cannot be distinguished from a non-2xx or malformed response for that incident.

## Traced flows

### Google

1. The `/login` page renders `StudentAuthForm`, initially selecting Google (or selecting from `?method=`).
2. `SocialLogin` calls `GET /auth/providers`. Production `API_PREFIX` is same-origin `/api`; `apps/web/next.config.ts` rewrites `/api/*` to the API origin selected by `NEXT_PUBLIC_API_URL` at build time.
3. With a client ID, the web page loads Google Identity Services (`accounts.google.com/gsi/client`) and renders its button. This is the only Google-facing browser step; the app uses an ID-token credential callback, not an app-owned OAuth redirect/callback route.
4. GIS callback submits `POST /auth/google` with `{ credential }`.
5. The API verifies the Google ID token’s RS256 signature against Google’s JWKS, issuer, audience, expiry, and verified-email claim. JWKS retrieval has a 10-second timeout and caches keys.
6. `SocialAuthService` resolves/creates the account and session. The route sets an HttpOnly session cookie; the client calls `refresh()` (`/auth/me`) and navigates to the profile, student dashboard, or admin route.

Thus the reported `providerLoadError` occurs **before the Google button/credential flow**, not during Google verification, after returning from Google, or while creating the session. If the button is reached but Google refuses to authenticate inside Telegram’s embedded browser, that is a distinct failure mode and has a dedicated safe Safari instruction in the updated UI.

Google’s published policy prohibits OAuth requests from embedded WebViews; Google states embedded webviews are blocked and recommends opening the sign-in in a supported external browser. This change does not attempt to bypass that policy. In a Telegram WebView, the Google button is now withheld and the user is told to use Telegram’s menu to open the page in Safari. Google GIS remains available in regular browsers. [Google policy announcement](https://developers.googleblog.com/upcoming-security-changes-to-googles-oauth-20-authorization-endpoint-in-embedded-webviews/)

### Telegram

1. The same provider-discovery request returns the bot username.
2. The web page loads Telegram’s legacy Login Widget script and registers `onDeborahTelegramAuth` as its callback.
3. The callback submits the widget data to `POST /auth/telegram`.
4. The API validates the body, recomputes Telegram’s HMAC-SHA-256 using SHA-256(bot token) and the alphabetically sorted data-check string, compares the hash in constant time, validates the timestamp (maximum age 24 hours, with a small future skew allowance), and validates the numeric Telegram ID.
5. `SocialAuthService` resolves/creates the Telegram identity and session. The API sets the HttpOnly cookie; client refreshes `/auth/me`, then routes as for Google.

There is no Telegram callback URL redirect in this implementation. The widget data callback posts directly to Deborah’s API. Existing backend tests cover valid/forged/stale payloads and successful cookie-backed session restoration. The implementation follows Telegram’s archived Login Widget signature guidance. Telegram’s current login documentation also describes a newer OIDC authorization-code/PKCE flow; switching libraries or protocols was not necessary to explain the shared message and was not done. [Telegram Login Widget guidance](https://core.telegram.org/widgets/login-legacy) [Telegram current login documentation](https://core.telegram.org/widgets/login)

The shared provider-load message is likewise **before** Telegram’s script/callback and signed payload verification. The updated UI reports script load failure separately, handles an explicit cancellation/error callback if the widget emits one, and no longer describes a failure of Deborah’s discovery API as failure to reach Telegram.

The Vercel project’s Production environment-variable names were inspected without decrypting values. `NEXT_PUBLIC_API_URL` and `NEXT_PUBLIC_DEMO_MODE` are present for Production; Vercel also has a sensitive `TELEGRAM_BOT_TOKEN` entry. The public discovery response proves the API currently returns Google and Telegram configuration; the API only does so for Telegram when both its bot token and username are configured. The API is hosted outside Vercel, so its `GOOGLE_CLIENT_ID`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `WEB_ORIGIN`, database URL, and session secret could not be directly audited in Render. No environment-variable values are included here. The token entry in Vercel is not used by the frontend and should not be copied into `NEXT_PUBLIC_*`; consider removing that duplicate from Vercel after confirming it is not used by another function.

Verify these production settings in their respective platforms (keep secrets in the API secret store):

- **Vercel web project:** Production entries for `NEXT_PUBLIC_API_URL` and `NEXT_PUBLIC_DEMO_MODE` are present. The live provider route returned HTTP 200 after the deployment. The actual value of `NEXT_PUBLIC_API_URL` was not decrypted; verify it is the API origin only (scheme + host, no `/api` or trailing slash).
- **API host:** `GOOGLE_CLIENT_ID`; `TELEGRAM_BOT_TOKEN` (secret); `TELEGRAM_BOT_USERNAME` (public bot username without `@`); and `WEB_ORIGIN=https://web-cdry.vercel.app` for exact-origin CSRF/CORS policy. Existing API startup also requires `DATABASE_URL` and `SESSION_SECRET` (at least 32 characters).
- **Google Cloud OAuth client:** web application client ID must match `GOOGLE_CLIENT_ID`; add `https://web-cdry.vercel.app` as an Authorized JavaScript origin. This GIS ID-token flow has no Deborah OAuth redirect/callback URL to configure. Do not place a Google client secret or Telegram bot token in `NEXT_PUBLIC_*` variables.
- **Telegram @BotFather:** link the bot to the exact website domain with `/setdomain` for the legacy widget. For Telegram’s newer OIDC product, its separate allowed-origin/redirect URI configuration would apply; this code does not use OIDC callback URLs.
- **Session cookie:** production API issues `HttpOnly; Secure; SameSite=None; Path=/` by default. Browser traffic uses the same-origin web proxy, so the browser cookie is under the web origin instead of depending on third-party cookies. Keep the default unless the web and API are deliberately deployed under the same registrable site and deployment has been verified for that topology.

No middleware or redirect loop was found in the message path. The same-origin rewrite design avoids relying on cross-site browser cookies. Backend cookie and authenticated `/me` behavior are covered by integration tests; a real iPhone cookie/session round trip was not possible here.

## Changes made

- `apps/web/features/live/AuthForms.tsx`: accurately reports provider-discovery errors without attributing them to the selected identity provider; adds an explicit retry; distinguishes invalid/unavailable provider callbacks from post-auth session restoration failure; reports Telegram widget script-load errors and explicit cancellation; prevents starting Google sign-in in Telegram’s embedded browser and gives a Safari fallback.
- `apps/web/features/live/auth-support.ts`: shared pure helpers for these messages, cancellation recognition, and Telegram-WebView detection.
- `apps/web/tests/auth-support.test.mjs`: tests network/HTTP discovery failures, provider callback errors for both providers, session failures, cancellation, and Telegram user-agent behavior.
- `apps/api/tests/social-auth.test.ts`: tests Google JWKS network outage maps to 503 without issuing a session cookie, and a session-creation failure returns an error without issuing a cookie. Existing tests already cover invalid Google/Telegram callbacks, the Telegram HMAC/timestamp checks, successful sessions, cookie attributes, and disabled providers.
- `docs/AUTHENTICATION_WEBVIEW_INVESTIGATION.md`: this report.

No authentication library, token verification, account-linking behavior, provider secret, API session policy, routing, or existing Safari Google flow was replaced or weakened. The changes were committed as `d4293843607c4f3a03f9a7f24fe67867309192de` and deployed to the Vercel production alias.
